# Loot Drop 分析报告

适用于 `loot-drop.io` / `www.loot-drop.io` 的 `/startup/<编号或名称>` 报告。阅读全文后生成摘要和有实质内容的中文飞书分析文档，保留原文与飞书双链接；来源为 `Loot Drop`，默认类型仍为 `article`。用户在 2026-10-27 补充了下述命名与正文质量要求。

## 公司名与报告标题

- 报告名称固定为 **`{公司名称} Loot Drop 分析`**。数据库 `title` 与飞书文档标题一致；不再采用“公司名｜创业失败案例”“公司名｜中文要点”等旧名称。
- 公司来自中国时，先实时联网核实其通用中文名称，优先公司官网、官方账号或公开公司资料，不能仅按英文发音猜译。原报告使用品牌名时采用该品牌的中文名，正文另交代品牌与运营主体关系，不把品牌与法人混为一谈。
- 示例：CodeMao 的中文品牌名为“编程猫”，所以标题是 **`编程猫 Loot Drop 分析`**。核实依据：[点猫科技（编程猫）官网](https://www.codemao.cn/)，官网注明其运营主体为深圳点猫科技有限公司。此例是命名方法，不作为其他公司的名称字典。
- 非中国公司保留其原有公司名；查不到可靠中文名时保留原名并说明未核实，不造名字。正文保留原报告名称和原文链接，并附中文名的核实来源。
- `fetch.mjs` 的标题是原始线索；Agent 核实公司名后构造上述 `title`，再交给 keeper。helper 已将 `title` 用于飞书创建标题和数据库保存。不要只改正文一级标题，导致飞书页面标题仍是旧名称。

## 全文读取与摘要

按 [workflow.md](workflow.md) 先查原链接，再查来源与拟定标题。已有收藏不自动覆盖；本次仅修改 Skill 不等于获准更新旧记录或重写已有飞书文档。

用 `fetch.mjs URL 系统临时输出目录` 获取原始 HTML、article.md 和 metadata.json；阅读全文，核对 `loot_drop_sections`、折叠区与末尾。六个分析卡片的完整文字在 `.grid-card[data-full-text]`，不能拿卡片短预览写正文。提取器已展开该字段，保留重建方案、技术清单和相关公司的 `data-href`。遇到 `loot_drop_incomplete` 或内容截断时，用已有授权浏览器逐项展开；未取得完整内容时说明缺失，不能宣称已读全。

摘要直接依据原报告，遵守 [abstract.md](abstract.md) 的未读者视角与 **400 个 Unicode 字符**上限：先说明公司做什么，再解释报告讨论的问题及核心思路。摘要与飞书正文分别撰写；400 字符不限制飞书正文。

## 正文深度与处理范围

正文应让未读原文的人理解业务与分析依据，不能只剩“政策风险、成本高、AI 重建”几句空泛要点。对选定的观点说明对象、机制、证据或例子、适用条件和限制；必要术语随文解释。涉及金额、比例、年份、价格、指标或预算时核对单位、口径及其属于实际结果还是预测，不用“很多、较高、多项”等词替代需要保留的关键信息。

- **用户提供了全文，或内容具有允许本次使用的转载授权时**：可以完整翻译或用自己的语言充分改写，逐项保留事实、推理、数据、例子、阶段方案和限制条件；不是把各模块压成一句总结。对照下面的覆盖表查漏补缺。
- **只有外部链接、不能完整转载时**：用自己的结构写独立分析，在允许范围内概述关键主张、选取有代表性的事实，加入解释、评估与可核实的外部依据。说明其为分析而非全文译本；不能靠换词把整篇文章无损复刻，也不能承诺覆盖每个细节成为原文替代品。若用户要求无信息损失的全文版本，简短说明需要其提供全文或相应授权，不能把几条要点冒充完整交付。
- 在两个模式中都区分“报告声称”“独立核实的信息”和“本次分析”。公司名核实时发现官方信息与原报告存在矛盾，应分别列明来源与日期；不把报告中的倒闭、违法等判断写成已确认事实，也不悄悄删除或改成相反结论。

## 内容覆盖核对

以下用于识别遗漏及决定分析重点；完整处理授权正文时逐项覆盖，独立分析时覆盖关键主题，不逐项复述全部原文。篇幅随实际信息量决定，不按范例固定条数。

| 内容 | 应讲清的关系与细节 |
| --- | --- |
| 公司业务与概况 | 服务谁、解决什么问题、产品怎样运作、怎样收费，以及国家、行业、产品类型、成立/结束年份、融资或资金消耗的原文口径 |
| 失败原因 | 事件顺序、原因如何传导到收入/成本/现金流、具体证据与例子；区分导火索、长期问题和报告推测 |
| 市场与竞争 | 当时与现在的变化、竞争者及替代方案、细分需求和行业条件；不能只说“竞争激烈” |
| 创业启示与市场潜力 | 建议为什么成立、适用前提、市场规模/增长预测的依据与不确定性，评分存在时保留其含义 |
| 重建难度与扩展能力 | 技术、内容、合规、获客和交付各自的难点；增长是否伴随成本增长，条件与评分是否仅为报告判断 |
| 转型/重建方案 | 面向客户、价值主张、产品能力、切入方式、地区选择、竞争优势及取舍；方案不能写成既成成果 |
| 技术建议 | 报告所列技术及对应用途，解释其在方案中的作用；不把历史选型当作当前工具推荐 |
| 执行计划 | 各阶段做什么、交付物、目标与指标、预算、人员、时间；原文未给出的项目标明未提供，不自行编造 |
| 收入与单位经济 | 收入来源、价格、抽成、计费周期、转化与留存假设、获客成本/客户终身价值、收入目标；预测不写成已实现 |
| 相关案例 | 对应公司名称及原报告链接，不因页面链接藏在 data-href 而漏掉 |

草稿写完后逐节回到来源核对：主要主题是否遗漏，关键结论有没有解释依据，数字是否有单位和条件，建议是否保留适用范围。完整模式核对逐项覆盖；独立分析的取舍和范围如实说明。需要临时核对笔记时只放系统临时目录，不增加工作区报告文件。

## 飞书排版与回读

以用户的 [Orbital Express 原页](https://www.loot-drop.io/startup/2540-orbital-express) 和 [飞书排版范例](https://lcn6mqfic6vj.feishu.cn/docx/BKyfd6iXdo7HaixTu4fch1pUnVf) 参考表格、模块层级和列表表现，不把范例正文或条数套到其他公司。

- 文档标题采用上面的固定名称；开头给原文入口、公司身份及必要来源。正文标题组织为有意义的大模块。
- 概况用两列表格（类别 / 内容）；主要分析模块用大标题，段落讲清因果关系，适合并列比较的内容使用列表。
- 并列能力、收入类别等使用原生编号列表，不保留大段 `(1)…(2)…` 手工数字。阶段标题保留顺序；相邻大模块之间留可见空白。
- 不复制网站导航、按钮、装饰图标、免责声明及“中文整理说明”；必要的事实限定随相关内容写明。正文不要自称“全文译本”或“完整转载”，除非实际满足该范围。

译稿、分析稿和核对材料放系统临时目录，沿用配置中的 lark-cli 身份及 profile。优先用 helper 创建、回读和恢复。回读时核对文档标题、文字覆盖、表格、原生列表、空白及相关链接；helper 的文字比对只能检查写入完整性，不能证明事实正确或分析充分。范例与旧文档未经明确更新要求不可覆盖。

## 入库与恢复

`source` 为 `Loot Drop`，默认 `source_type` 为 `article`；作者、原文发布时间只取明确元数据，不用成立/结束年份或飞书创建时间替代。`link` 保留原报告 URL；`copy_markdown_path` 指向本次飞书分析正文，或直接传已核对的 `copied_lark_link`。例如：

```json
{
  "title": "编程猫 Loot Drop 分析",
  "abstract": "实际读完报告后生成的不超过400字符中文摘要。",
  "source": "Loot Drop",
  "source_type": "article",
  "author": null,
  "source_created_at": null,
  "link": "https://www.loot-drop.io/startup/2554-codemao",
  "copy_markdown_path": "/系统临时目录/本次任务/analysis.md",
  "full_text_confirmed": true
}
```

`full_text_confirmed:true` 表示已获得并读完原报告，不表示独立分析稿是全文副本。原文与飞书分析链接同时保存；分析稿不能替代缺失的原文入口。

副本失败或回读不完整时不入库；数据库失败沿用 jobs 记录复用原文档，创建结果不确定时先查实际文档，不盲目新建。明确更新时只传用户要求的字段；仅改摘要不重建副本。收尾清理本次临时目录，保留配置、文档和恢复状态。
